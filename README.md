# Cue

Cue is a local-first assistant demo. The browser performs MiniLM embedding and local intent resolution; a Python service provides a session-isolated SQLite provider registry, mock execution, and retrieval. Providers own their manifests and adapters. Provider results use the versioned Cue Display Document contract.

## Run locally

1. Install Node.js 20+ and Python 3.11+; run `npm install`.
2. Build and verify the synthetic baseline with `npm run seed:demo` and `npm run verify:demo`.
3. Start the backend using `npm run backend` and the UI with `npm run dev`. Open the Vite URL in a supported Chromium browser.
4. Select an AI mode, then choose a demo scenario or enter a request. Web AI uses browser-side retrieval and deterministic resolution only. Automatic keeps decisions local unless tool selection remains ambiguous or eligible argument normalization needs its hosted fallback. Always Dots 3 sends the request, registered tool schemas, matching provider-data evidence, and pending context to OpenRouter for planning. All tool execution remains in Cue's backend and uses the registered provider adapters. If a hosted plan is awaiting confirmation, confirm its exact arguments or cancel and submit a new request to change them.
5. Use **Reset demo session** to restore that browser session's SQLite working copy to the packaged baseline.

The synthetic providers require no personal Anki files. Hosted modes require an OpenRouter API key; without one, hosted reasoning fails explicitly, while Automatic can still use the local Gemma fallback for eligible argument normalization. The microphone and optional Bangle.js connection remain available; transcript entry is the simplest way to run scenarios.

To configure OpenRouter, put `OPENROUTER_API_KEY=your-key` in the project-root `.env` before starting the backend. The backend loads `.env` at startup; process environment variables take precedence. Supported backend settings are simple `KEY=value` entries with optional single or double quotes; quote values containing `#`. `.env.example` lists the optional backend port and synthetic database paths. If you change `BACKEND_PORT`, restart both the backend and Vite so the proxy uses the same port. Do not use a `VITE_` variable for the key.

If the UI reports that the backend does not support conversation state, stop the running backend and start it again with `npm run backend`. The Python server does not automatically reload code changes; an older process may not have the current API routes.

## Database and deployment

- `data/cue_demo.db` is built exclusively from `data/seed/provider-manifests.json`, `provider-data.json`, `tool-manifests.json`, `tool-retrieval-config.json`, and the normalized float32 `tool-embeddings.f32` fixture plus its content-hash index. It contains six synthetic providers, 18 tools, 12 illustrative Anki cards, 6 knowledge records (documents and chunks), 3 web results, 5 Calendar events, 3 notifications, 2 alarms, one asset, and 177 typed tool retrieval records. The 62 unchanged tool vectors are seeded; remaining tool vectors and provider-owned record vectors are generated in the browser and stored only in the session database.
- Seeding is repeatable and never opens or migrates `semantic_mastery.db` or `cue_memory.db`. Personal databases, SQLite sidecars, and Anki exports remain ignored by Git; the synthetic baseline is explicitly unignored.
- `CUE_DEMO_SEED_DB` selects the packaged baseline. `CUE_DEMO_RUNTIME_DIR` selects writable session storage; its default is a temporary-directory location, not the application directory. The baseline is opened read-only and copied into a separate database named from a hash of the HTTP session. Mock writes and browser-computed embeddings affect only that copy. Reset replaces it from the baseline.
- Deploy the backend code together with the committed `data/cue_demo.db`; set `CUE_DEMO_SEED_DB` if the packaged file is at another path and provide a writable `CUE_DEMO_RUNTIME_DIR`. The application package may remain read-only. No developer collection, local migration, external service, or credential is needed.

## Architecture

- `demo_database.py` builds the clean SQLite schema, exposes provider manifests/data, stores browser-generated vectors, searches the separate `tool` and `provider-data` namespaces, validates arguments, and resolves trusted adapter IDs. Provider-data vectors are keyed to provider-owned records and refreshed when their source content changes; they can ground argument/entity resolution and hosted plans but never enter the local tool-similarity ranking or authorize execution. `backend.py` never imports the legacy personal-database module.
- Each registered provider has its own Python adapter in `demo_providers/`; providers own Anki, Knowledge, Web Search, Calendar, Notifications, and Alarm behavior. Tool definitions, keywords, examples, schemas, and retrieval vectors are loaded from SQLite rather than a Cue-side domain catalogue.
- `src/intelligence/` performs top-K description/keyword/example tool retrieval followed by separate provider-data lookup, then deterministic schema-driven argument resolution. It retains argument provenance, asks for missing or ambiguous values, validates schemas, requires confirmation, and dispatches only registered provider adapters. Local multi-step workflows and Dots 3 proposals use the versioned `cue.execution-plan` contract with dependencies, JSON Pointer bindings, allowlisted transformations, conditions, operation statuses, and an eight-operation cap. Plans execute sequentially; missing dependency results skip dependent operations, and only the exact pending side effect can be confirmed. Calendar queries support timezone-aware, end-exclusive date ranges and a persisted Monday/Sunday week-start preference. Conversation state and idempotent operation results are session-scoped in SQLite, so clarifications and confirmations can resume after reload without repeating side effects. Similarity only ranks candidates; it never authorizes execution. Aggregation weights, thresholds, and operation limits are configured in `data/seed/tool-retrieval-config.json`.
- Tool retrieval uses local MiniLM embeddings. A multilingual cross-encoder is loaded lazily and runs only when MiniLM results remain ambiguous; its sigmoid-normalized scores are ranking scores, not calibrated probabilities. Its initial routing thresholds are a minimum top score of 0.20 and, when there is a second candidate, a margin of at least 0.10. These values in `data/seed/tool-retrieval-config.json` are provisional, not empirically calibrated confidence levels.
- Cross-encoder status displays loading and per-file download progress; the status log records reranking, backend retries, failures, and uncertain scores. It tries WebGPU when an adapter is available and retries on WASM if initialization or inference fails; both use the same q8 `onnx/model_quantized.onnx`. WebGPU may still execute unsupported operators on WASM. There is no cross-encoder deadline, so a stalled download or inference can delay the existing fallback.
- The AI mode selector is persisted in browser localStorage. Web AI uses browser-side retrieval, deterministic resolution, and local Gemma when suitable; it never sends prompts to OpenRouter. Automatic uses local retrieval and Gemma first, with hosted fallback only for eligible normalization or unresolved tool ambiguity. Always Dots 3 uses the backend `/api/demo/reason` endpoint with the configured OpenRouter model to propose a structured plan; the backend validates tool IDs, schemas, dependencies, bindings, operation limits, and confirmation policy before Cue executes anything. Matching provider-data evidence is retrieved in the session database using a browser-generated query embedding, with a bounded set of records included in the prompt. Hosted requests may contain the user's request, conversation context, registered schemas, or matching provider records. Do not enter sensitive information while hosted features are enabled. Gemma runs in a dedicated MediaPipe worker behind a WebGPU/desktop capability gate, which uses browser estimates rather than measured VRAM.
- `src/display/schema/cue-display-v1.schema.json` defines Cue Display Document v1 using JSON Schema Draft 2020-12. The shared validator checks nested elements, actions, asset references, and registered-tool arguments before rendering. The React renderer interprets semantic tokens and never executes provider code.

## Watch and tests

The web app installs `watch/bangle-app.js` through the Espruino Nordic UART BLE service and transfers the validated Cue Display Document JSON. At 176×176 the watch adapts nested text, icons, lists, and page content to wrapped, scrollable pages; image elements show their alternative text because watch image decoding is not implemented. On a clarification screen, tap an offered choice or **Speak instead** to capture the last 10 seconds and transcribe a reply into the pending request. Tapping a displayed action sends its registered action ID back to Cue; side-effecting actions require confirmation in the browser or on the watch. Run `npm test`, `npm run build`, `npm run verify:demo`, and `py -3.14 -m unittest discover -s tests -v` for automated checks. `data/seed/tool-routing-benchmark.json` supplies synthetic English/Finnish positive, ambiguous, and no-tool cases; `src/intelligence/retrieval/benchmark.js` evaluates them when given the real browser embedding callback. The watch UI and installation commands have been exercised in the official Bangle.js 2 emulator with a mocked transport; this does not verify physical BLE behavior. Real Android/calendar/web integrations and image-to-watch optimization/transfer are intentionally out of scope.

If installation fails while the watch shows “Reloading...”, restart it by holding its button for about six seconds and releasing when pixelated text appears, then reconnect. See the [Bangle.js 2 reset instructions](https://www.espruino.com/Bangle.js2#resetting). Do not select Factory Reset; it erases watch data.

Display delivery waits up to 10 seconds for acknowledgement after each full transfer and retries up to three times. Install the updated watch app to retain partial transfers while chunks continue arriving.
